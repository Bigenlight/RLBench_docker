# TGM-VLA overlay — development notes

This file documents **why** the TGM-VLA overlay (`vla/tgm_vla/`) is shaped
the way it is. The README is the user-facing reproduction recipe; this
file is for the next developer who needs to **modify** the overlay, debug
a regression, or apply the same approach to a different VLA.

Everything below was learned the hard way during the May 2026 bring-up.
The end-to-end smoke test that backs every claim here is:

```bash
docker run --rm --gpus all --user "$(id -u):$(id -g)" \
    -e HOME=/workspace/hf_cache -e NVIDIA_DRIVER_CAPABILITIES=all \
    -v "$HOME/TGM-VLA:/workspace/TGM-VLA" \
    -v "$HOME/.cache/huggingface:/workspace/hf_cache" \
    tgmvla:latest bash -c 'cd /workspace/TGM-VLA/tgm_vla &&
        python tools/test_rlbench.py \
            --model-folder /workspace/TGM-VLA/runs/tgmvla_test \
            --model-name model_rlbench.pth \
            --eval-datafolder /workspace/TGM-VLA/data/rlbench/test \
            --tasks open_drawer push_buttons close_jar \
            --eval-episodes 1 --start-episode 0 --episode-length 25 \
            --log-name smoke --device 0 --headless --save-video'
```

Expected: Score 100/100/100, three mp4s under `runs/tgmvla_test/smoke/
model_rlbench/videos/`, all files host-UID owned, no root cruft in the
bind-mount.

## 1. Architecture — why overlay, why bind-mount

**Overlay pattern** (`vla/<name>/Dockerfile + entrypoint + patches + README`).
Same as `vla/bridgevla/`. The alternative — a single monolithic image with
all VLAs vendored — would force a global version-pin compromise: BridgeVLA
wants PaliGemma + torch 2.4, TGM-VLA wants torch 2.1 + pytorch3d. The
overlay pattern lets each VLA freeze its own venv.

**Bind-mount the TGM-VLA source tree (`~/TGM-VLA → /workspace/TGM-VLA`)
instead of `COPY`-ing it into the image.** Three reasons, in order of
importance:

1. **`point-renderer` compiles a custom CUDA op at install time.** Baking
   it into the image freezes the compile against whatever CUDA toolkit
   was present during `docker build`. Compiling at first container start
   keeps the compile under our control without coupling it to image
   build state. (Note: this does NOT give you the freedom to bump
   torch / CUDA / pytorch3d — see the pin matrix in §2.)
2. **Model-code iteration**. Editing files in `~/TGM-VLA` on the host is
   immediately visible inside any running container — no rebuild loop.
3. **The vendored libs (`PyRep`, `RLBench` fork, `YARR`, `peract_colab`,
   `robot-colosseum`, `point-renderer`) total ~1.5 GB of git history**.
   Baking them would bloat the image and the build context.

**What IS baked into the image:**
- All pip dependencies of TGM-VLA's `setup.py` (so first-run is
  `--no-deps` for everything → fast).
- CoppeliaSim 4.1.0 Edu (~700 MB, network-fetched, immutable).
- SAM2 `hiera_base_plus` checkpoint (~309 MB). Symlinked (not copied)
  into the bind-mount at first run so TGM-VLA's hard-coded relative path
  resolves. Symlink because (a) it's idempotent across multiple
  containers sharing the same bind-mount, and (b) a copy would silently
  duplicate ~309 MB into the host repo. Caveat: if a future user prunes
  the image layer containing `/opt/sam2_ckpts/`, the symlink dangles —
  the README documents how to manually download a replacement.

**What lives in the bind-mount:**
- TGM-VLA source + vendored libs.
- Compiled `point-renderer` `.so` (lives in the source tree because
  `pip install -e` of a source dir writes `__pycache__` and built
  artifacts in-tree).
- `.egg-info` directories, generated by the `pip install -e` step.

## 2. The dependency pin matrix

Every pin in `Dockerfile` has a specific failure mode if violated. The
ones that are NOT obvious from the upstream README:

| Pin | Where | Why this exact version |
|---|---|---|
| `setuptools<81` | venv-create RUN (line 104) | `point-renderer/setup.py` does `from pkg_resources import packaging`. setuptools 81 removed `pkg_resources.packaging`. Pinning in the same RUN as `pip upgrade` means a transient later `pip install` cannot satisfy a fresh wheel by bumping setuptools first. |
| `numpy==1.26.4` (pinned **twice**) | lines 167, 193 | torch 2.1.0 wheels were built against the NumPy 1.x C ABI; numpy ≥ 2 changes the array struct layout → segfault on first cuda tensor op. The second pin guards against transitive upgrades from the heavy deps RUN (YARR's `setup.py` requests `numpy>=1.23`, which pip may satisfy with 2.x). |
| `opencv-python-headless==4.11.0.86` | line 173 | The non-headless `opencv-python` ships its own Qt5; under Xvfb that Qt5 conflicts with CoppeliaSim's bundled Qt5 and one of them fails to load `libqxcb.so`. YARR's `setup.py` drags in `opencv-python` transitively, so the entrypoint **uninstalls both `opencv-python` and `opencv-contrib-python`** after the full first-run install completes (`entrypoint.sh:100`, run once after all six vendored libs + the main `tgm_vla` package finish installing). The headless build baked into the image then remains the only opencv. |
| `torch==2.1.0 + torchvision==0.16.0 (cu121)` | line 155-156 | TGM-VLA's paper pins this. `pytorch3d 0.7.5` prebuilt wheels only exist for the exact `py310_cu121_pyt210` triplet. Any other combo means building pytorch3d from source (~40 min). |
| `transformers==4.49.0` / `bitsandbytes==0.38.1` / `hydra-core==1.3.2` | line 179-181 | TGM-VLA's `setup.py` versions. Have not personally verified what newer versions break — left as-is because upstream specifies them. Do not bump without re-running the smoke test. |
| CLIP from `git+https://github.com/openai/CLIP.git` | line 190 | No official PyPI release. TGM-VLA's `setup.py` uses this URL. |
| CoppeliaSim **4.1.0** Edu, **Ubuntu20_04** binary | line 113-116 | PyRep's C extension is symbol-pinned to 4.1.0; newer CoppeliaSim → segfault on first PyRep call. Ubuntu 20.04 binary works on the Ubuntu 22.04 base because glibc is forward-compatible. CoppeliaSim never released a 22.04 build for 4.1.0. |

## 3. CoppeliaSim under headless / Xvfb — the Qt path

This was the single most expensive bug to diagnose during the original
`docker/` standalone setup (carried over here verbatim):

```dockerfile
ENV LD_LIBRARY_PATH=${COPPELIASIM_ROOT}:${LD_LIBRARY_PATH} \
    QT_QPA_PLATFORM_PLUGIN_PATH=${COPPELIASIM_ROOT}/platforms \
    QT_PLUGIN_PATH=${COPPELIASIM_ROOT}
```

Without `QT_PLUGIN_PATH=$COPPELIASIM_ROOT`, CoppeliaSim's bundled Qt5
cannot find the `xcbglintegrations/` directory. Symptom: **all vision
sensor framebuffers return all-zero (black) images**, the simulator does
not crash, and the eval looks like it's running normally — you just get
zero rewards on every task. See `docker/README.md` § "Why
QT_PLUGIN_PATH" for the full root-cause writeup.

The `libcoppeliaSim.so.1 → libcoppeliaSim.so` symlink is pre-created
during `docker build` (line 122). PyRep's `cffi_build/cffi_build.py`
tries to create this symlink during `pip install -e`, which runs as the
calling UID under `--user`. Without the pre-creation, `--user` mode hits
PermissionError on the root-owned `$COPPELIASIM_ROOT` and the install
fails before any code runs.

## 4. Entrypoint — install detection by import, not by file

The entrypoint installs the six vendored libs on first container start
and skips them on subsequent starts. The skip-condition used to be a
sentinel file `~/TGM-VLA/.tgmvla_libs_installed` written into the
bind-mount. **This is wrong** if the user ever rebuilds the image:

- Image rebuild → fresh `/opt/venv` with nothing installed.
- Bind-mount still has the marker file from a previous container.
- Entrypoint sees the marker, skips install.
- Container runs with an empty venv → `ModuleNotFoundError: rlbench`.

The fix (in `entrypoint.sh`):

```bash
need_install=1
if python -c "import rlbench, pyrep, point_renderer, tgm_vla" 2>/dev/null; then
    need_install=0
fi
```

This tests the **current** venv, not a marker that outlives the venv.

Two related entrypoint details:

- **Patches are applied with `patch -p1 -N --silent ... || true`.** `-N`
  ignores already-applied hunks so a re-run against the same bind-mount
  source doesn't crash. `|| true` swallows the non-zero exit `-N`
  produces when every hunk is already there.
- **Xvfb start is gated on the X socket existing, not on `$DISPLAY`
  being empty.** `Dockerfile` sets `ENV DISPLAY=:99`, so `$DISPLAY` is
  always populated. The actual check is `[ -e "/tmp/.X11-unix/X${dpy_num}" ]`
  — if the socket exists, an X server is already there (host X mount,
  or another Xvfb); if not, we start one.

## 5. The three test_rlbench.py patches

The upstream eval script has three bugs that only fire when you actually
try to save videos. They're all in `tgm_vla/tools/test_rlbench.py`. We
patch via `vla/tgm_vla/patches/*.patch` rather than maintaining a fork.

### Patch 01 — `record_enabled=False` → `args.save_video` + direct save

`record_enabled=False` is hard-coded in the `episode_rollout` call.
Without this flag YARR's rollout generator never attaches camera frames
to transitions, so even with `--save-video` upstream produces zero
videos.

But fixing `record_enabled` alone is not enough. Upstream's
`save_results` function looks for `VideoSummary` objects in the
post-task `summaries` list, which is populated by
`stats_accumulator.pop()`. That accumulator drains per-episode
`VideoSummary` objects out of the transitions before `save_results`
sees them — they're consumed and gone.

The patch saves videos **inline, immediately after `episode_rollout`
returns**, by iterating `transition.summaries` directly while the
`VideoSummary` objects are still alive:

```python
for _t in episode_rollout:
    for _s in getattr(_t, "summaries", []):
        if isinstance(_s, _VS):
            _vid = _s.value
            ...
            _writer = _cv2.VideoWriter(_path, _fourcc, 25, (_W, _H))
            for _f in _vid:
                _writer.write(_f.astype("uint8"))
```

### Patch 02 — `task_score = "unknown"` → `mean(task_rewards)`

The `else` branch of `save_results` (when `summaries` has no
`eval_envs/return/<task>` entry) returns the **string** `"unknown"`.
`main()` later does `sum(scores) / len(scores)` to compute the overall
average → `TypeError: unsupported operand type(s) for +: 'int' and 'str'`.

This isn't an edge case. On a single-task eval the matching
`eval_envs/return/<task>` summary often isn't in the accumulator
(timing depends on when YARR flushes), and the `else` fires on every
run. Patch returns `mean(task_rewards)` (falling back to 0.0 if empty)
so the outer `sum` always sees floats.

### Patch 03 — disable the second `if args.save_video:` block

After our patch 01 saves videos inline, the original `save_results` still
has its own `if args.save_video:` block at line 312 that indexes
`task_rewards[video_cnt]`. `video_cnt` is incremented while scanning the
flattened cross-episode `summaries` list, and the index quickly diverges
from `task_rewards` (which is per-episode). Result: `IndexError` partway
through saving. Patch wraps the entire block in `if False and
args.save_video:` — patch 01 already saved the videos correctly, so
this block is just dead.

> Why not delete instead of dead-code? Keeping the upstream lines makes
> the patch trivially reversible if a future TGM-VLA release fixes the
> indexing, and minimizes the diff size for future rebases.

## 6. `--user $UID:$GID` mode — the four gotchas

The README's recommended `docker run` uses `--user "$(id -u):$(id -g)"`
so files written into `~/TGM-VLA` stay editable on the host. Four things
have to align for this to work:

1. **`/opt/venv`, `/opt/sam2_ckpts`, `/opt/tgmvla_patches`, `/workspace`
   must be world-writable.** Done by `RUN chmod -R a+rwX ...` in the
   Dockerfile (line 231). The image is built as root, so these dirs are
   root-owned by default. Without the `chmod`, a `--user $UID:$GID`
   container's first-run `pip install -e` PermissionErrors when writing
   into `/opt/venv/lib/python3.10/site-packages/` (the venv) and into
   the bind-mount's `.egg-info/` dirs (host-owned). Root mode would work
   either way; this is purely a `--user` accommodation.
2. **`/opt/coppeliasim/libcoppeliaSim.so.1` symlink must exist before
   PyRep's setup.py runs.** PyRep's `cffi_build.py` tries to create it
   and PermissionErrors on the root-owned dir under `--user`. Pre-created
   in the Dockerfile (line 122).
3. **`HOME` must be writable.** Without `-e HOME=...`, HOME defaults to
   `/` for UIDs not in the container's `/etc/passwd`. CLIP downloads to
   `~/.cache/clip` → `/.cache/clip` → PermissionError; matplotlib
   PermissionErrors on `/.config/matplotlib`. README pipes
   `-e HOME=/workspace/hf_cache` (which is already a bind-mounted
   writable dir).
4. **Host UID must own `~/TGM-VLA`.** Trivially true after `git clone`,
   but if anyone has previously run the container as root and written
   into the bind-mount, those root-owned `.egg-info` directories
   trigger "Cannot update time stamp" errors from setuptools. Fix:
   `docker run --rm -v ~/TGM-VLA:/data alpine chown -R $(id -u):$(id -g) /data`.

## 7. Quick diagnostics

When something breaks in a way that isn't an obvious traceback, these
are the first three things to check:

- **All tasks score 0/N (or every reward is exactly 0.0)**: vision
  sensors are probably returning all-zero frames. Verify the
  `QT_PLUGIN_PATH=$COPPELIASIM_ROOT` env is set inside the container
  (`docker exec ... env | grep QT`). Inside an interactive shell,
  instantiate any vision sensor and dump one frame —
  `cv2.imwrite("/tmp/dbg.png", frame[..., ::-1])`. If it's pure black
  the Qt plugin path is broken; if not, the model is genuinely
  failing.
- **`pip install -e ... PermissionError`**: ownership mismatch on the
  bind-mount. `ls -la ~/TGM-VLA/.git/HEAD` — owner UID must equal
  `id -u` on the host. If a prior root-mode container left root-owned
  cruft, run
  `docker run --rm -v ~/TGM-VLA:/data alpine chown -R $(id -u):$(id -g) /data`.
- **`ModuleNotFoundError: rlbench` on first command after a `docker
  build`**: the entrypoint thinks the libs are installed (it isn't —
  the import check should have caught this). Check that the entrypoint
  copied into the new image matches `vla/tgm_vla/entrypoint.sh` —
  `.dockerignore` exclusions sometimes regress.

A successful smoke run on RTX 3060 12 GB takes ~35 s end-to-end for the
3-task eval, and writes three mp4s of ~400 KB each. Reference outputs
are committed at `vla/tgm_vla/examples/smoke/`:

```
examples/smoke/
├── close_jar_success_ep0.mp4      (~419 KB)
├── open_drawer_success_ep0.mp4    (~424 KB)
└── push_buttons_success_ep0.mp4   (~401 KB)
```

These were generated on 2026-05-28 with the current `Dockerfile` +
`entrypoint.sh` + patches against the
[upstream TGM-VLA HEAD as of that date](https://github.com/PuFanqi23/TGM-VLA).
If a future eval changes resolution, fps, or task list, regenerate them
and replace; if it merely changes pixel values, leave them.

## 8. Pitfalls encountered during bring-up (don't redo these)

- **Don't use `numpy>=2`**. Segfaults on first cuda tensor op under
  torch 2.1.0. Already pinned twice in Dockerfile.
- **Don't install non-headless `opencv-python`**. Conflicts with
  CoppeliaSim's Qt5 under Xvfb. The entrypoint actively `pip
  uninstall`s it after YARR pulls it in.
- **Don't use `pip install` without `--no-deps`** in the entrypoint.
  Letting pip re-resolve drags in numpy 2 / opencv-python / etc.
- **Don't build pytorch3d from source**. The `py310_cu121_pyt210`
  prebuilt wheel exists; use the fbaipublicfiles index URL exactly as
  written. From-source build needs the full CUDA devel image (~4 GB
  bigger) and takes 40+ min.
- **Don't pass `--tasks open_drawer,push_buttons,close_jar` to
  `test_rlbench.py`**. Its argparse spec is `nargs="+"`, so it expects
  space-separated. (The comma form *does* work for
  `dataset_generator.py` from RLBench's tools/ — different parser.)
- **Don't trust the pre-existing `~/TGM-VLA/runs/tgmvla_test/`
  directory after debugging**. Each run creates a new `<log-name>/`
  subdir, but the videos directory inherits patches state from the
  bind-mount source files at the time the eval started — if you
  edited a patch mid-debug, your earlier mp4s may have stale behavior.
- **Don't put the install marker in the bind-mount**. Image rebuilds
  leave the marker behind and skip install. Use an `import` check.

## 9. Adding the next VLA — minimal checklist

If you're cloning `vla/tgm_vla/` as a template for the next VLA:

1. Copy the directory, rename. Keep the exact layout: `Dockerfile`,
   `entrypoint.sh`, `patches/`, `README.md`, `examples/smoke/`,
   `DEVNOTES.md`.
2. **`.dockerignore`**: add `!vla/<new_vla>/entrypoint.sh` and
   `!vla/<new_vla>/patches/` so they survive the `vla/*` blanket
   ignore.
3. **License gate**: rename the `ACCEPT_*_LICENCE` ARG. Don't reuse
   another VLA's arg name.
4. **Pin matrix**: torch / pytorch3d / numpy / opencv / CoppeliaSim. If
   the VLA uses a different torch version, the pytorch3d wheel index
   URL changes — see the `py<py>_cu<cu>_pyt<pyt>` pattern.
5. **Vendored libs**: list them in the order PyRep → point-renderer
   come last (need torch). Add `--no-deps --no-build-isolation` for
   any lib that builds a C/CUDA extension.
6. **Patches**: prefer `patch -p1 -N` over forking. The patches/
   directory must be `COPY`d into `/opt/<name>_patches/` and applied
   in the entrypoint inside the install gate.
7. **Smoke test**: at least 1 episode of 3 different tasks. Save the
   resulting mp4s to `examples/smoke/`. This is what proves the
   overlay works end-to-end.
8. **Update `vla/README.md`** lineup table and top-level `README.md`
   intro.
9. **Don't push the image to a public registry** (CoppeliaSim Edu
   license).
